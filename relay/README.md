# 日本出口の作り方 — 「声とも」を Render 経由で開くための最後の1ピース

> **何も入れたくない・クレカも使いたくない場合**
> → **[方法D: 日本の無料公開プロキシ](#方法d-日本の無料公開プロキシ何もインストールしない)**(実測で koetomo.fun が **HTTP 200** になったものを掲載)
> → **[方法C: ブラウザ拡張VPN](#方法c-ブラウザだけクレカ不要vpn拡張機能)**
> 恒久的に安定して使いたい場合は 方法A / 方法B です。

声とも (koetomo.fun) は **日本国外のIPを一律 403 で拒否** する地域制限を運用しています
(実測: 日本ノードのみ 200、他19カ国は全て 403)。そして **Render には日本リージョンが存在しません**。

つまり **Render 側で何を設定しても、日本の出口を1つ用意するまでは絶対に開けません。**
このフォルダはその「日本の出口」を作るためのものです。方式は2つあります。

| | 方式A: リバーストンネル(**おすすめ**) | 方式B:  forward リレー |
|---|---|---|
| クレジットカード | **不要** | 必要(Oracle は本人確認のみ・$0) |
| クラウド契約 | **不要**(手持ちの日本のマシンでOK) | 必要(Oracle Cloud 等) |
| ポート開放 / グローバルIP | **不要**(CGNAT でも可) | 必要(TCP 8443 開放) |
| 動かすもの | `relay/reverse-tunnel.js` を日本のマシンで常駐 | `relay/relay.js` を日本のサーバで常駐 |
| Render 側の設定 | `TUNNEL_TOKEN` 1つ | `RELAY_URL` + `RELAY_CA_B64` |
| 向いている人 | 日本で常時起動できるマシンがある | 日本の VPS を借りられる |
| 詳細 | ↓ このページの「方式A」 | ↓ 「方式B」 |

どちらでも **ブラウザで開く URL は Render のまま**(`https://koetomo.onrender.com`)。
日本のマシン/サーバは **暗号化されたバイト列を中継するだけ** で、TLS は
Render ⇔ koetomo.fun のエンドツーエンドのまま保たれます(中身を見られません)。

```
あなたのブラウザ
   │  https://koetomo.onrender.com      ← 見た目のURLは Render のまま
   ▼
Render プロキシ (Singapore 等)           … URL書き換え・Cookie・WebSocket中継
   │
   ├── 方式A: /__tunnel (ハブ) ←外向きWS── 日本のマシン (reverse-tunnel.js) ─┐
   └── 方式B: RELAY_URL ─────────────────→ 日本のサーバ (relay.js) ─────────┤
                                                                            ▼
                                                                     koetomo.fun(声とも)
```

# 方式A: リバーストンネル(クレカ不要・ポート開放不要)

## 仕組み(なぜポート開放が要らないのか)

日本の家庭回線は **グローバルIPが無い(CGNAT)** ことが多く、ルータのポート開放もできません。
そこで **接続の向きを逆にします**。日本のマシンから Render へ「外向き」の WebSocket を
張りっぱなしにし、Render 側は「その穴」を通じて日本から接続させます。

```
[日本のマシン]  ──外向き WSS(常時・自動再接続)──▶  [Render のハブ /__tunnel]
                                                          ▲
[Render のプロキシ] ──「koetomo.fun:443 に繋いで」────────┘
                                                          │ ハブが2本をペアリング
[日本のマシン] ──実際に日本の回線から koetomo.fun へ dial ─┘
```

- 日本のマシンは **受信を一切しません**(送信用の接続だけ)= ポート開放・グローバルIP不要
- ハブは TCP バイトを素通しするだけ = **TLS はエンドツーエンド**(ハブも日本のマシンも復号できません)
- Render 側は **`TUNNEL_TOKEN` を1つ設定するだけ**(ハブは server.js に内蔵済み)

## 手順1: トークンを作る

適当な32文字程度のランダム文字列を作ります(どちらか):

```bash
node -e 'console.log(require("crypto").randomBytes(18).toString("base64url"))'
openssl rand -hex 16
```

## 手順2: Render に `TUNNEL_TOKEN` を設定

1. Render ダッシュボード → 自分のサービス(koetomo-proxy)→ **Environment**
2. **Add Environment Variable**
   - Key: `TUNNEL_TOKEN`
   - Value: 手順1で作った文字列
3. **Save Changes** → 自動で再デプロイされます(1〜2分)

> `RELAY_ALLOW` は `render.yaml` で `koetomo.fun,ipinfo.io,ipwho.is,api.ipify.org` に
> 設定済みです。ハブはここに無いホストへの接続を拒否するので、踏み台にはなりません。

## 手順3: 日本のマシンでリレーを起動

**日本で常時起動しておけるマシン**なら何でも構いません(自宅PC / 実家のPC / Raspberry Pi / 常時ONのミニPC など)。
OS は Ubuntu / Debian などの Linux が一番簡単です(macOS も可、Windows は WSL2 推奨)。

```bash
# 1) リポジトリを取得(どこでもOK。relay/ フォルダだけあれば動きます)
git clone https://github.com/shunichi19990314/koetomo-proxy.git
cd koetomo-proxy/relay

# 2) 一発セットアップ(Node導入 → 設定保存 → systemd 常駐 → 状態表示まで自動)
bash setup-reverse-tunnel.sh wss://koetomo.onrender.com/__tunnel <手順1のトークン>
```

※ URL は **あなたの Render の URL** に置き換えてください(末尾に `/__tunnel` を付ける)。

手動で動かす場合はこれだけです:

```bash
HUB_URL=wss://koetomo.onrender.com/__tunnel \
TUNNEL_TOKEN=<手順1のトークン> \
node relay/reverse-tunnel.js
```

ログに次が出れば接続成功です:

```
[koetomo-relay] ✅ オンライン登録完了 (id=r1) — 待機ソケット 4 本を用意します
```

> **Node のバージョン**: Node 22 以上なら依存パッケージゼロで動きます。
> Node 20 / 21 の場合は `ws` が必要なので `cd relay && npm install` を実行してください
> (setup スクリプトが自動で判断して入れます)。

## 手順4: 確認する

1. `https://<あなたのRender>/__hub` を開く
   → `"relays": [ { "name": "...", "readySockets": 4 } ]` と出ていれば日本のマシンが接続済み
2. `https://<あなたのRender>/__status` を開く
   → ✅ **「上流に受け入れられています」** になれば完了
3. `https://<あなたのRender>/` を開く → 本家の声ともが動きます

## 運用メモ(方式A)

| こと | 挙動 |
|---|---|
| 日本のマシンがスリープ/電源OFF | 声ともが開けなくなります。**スリープ無効**を推奨(ネットワーク断は自動再接続します) |
| Render がスリープ(無料プラン15分) | リレーが数秒おきに再接続を試み、Render が起きたら自動で復帰します。最初の1アクセスは数十秒かかることがあります |
| 同時に何人使えるか | `RELAY_POOL`(既定4)が「即座に使える待機ソケット数」。不足分はハブが最大25秒キューイングし、リレーが自動補充します。家族数人程度なら既定で足ります |
| 回線が遅い/細い | `RELAY_POOL=2` に下げる、または音声系は帯域を食うので光回線推奨 |
| トークンを変える | Render の `TUNNEL_TOKEN` を変更 → 日本のマシン側の `/etc/koetomo-relay/env` も同じ値にして `sudo systemctl restart koetomo-relay` |
| ログ | `sudo journalctl -u koetomo-relay -f`(systemd)/ `tail -f ~/koetomo-relay.log`(nohup) |
| 停止 | `sudo systemctl stop koetomo-relay` / 完全削除は setup スクリプト末尾に記載 |
| 複数台 | 同じトークンで2台以上動かすと負荷分散されます(どちらか1台が生きていれば動きます) |

### うまくいかないときの切り分け

| 症状 | 原因 / 対処 |
|---|---|
| `/__hub` の `relays` が空 | 日本のマシンでリレーが起動していない。ログを確認(`journalctl -u koetomo-relay -n 50`) |
| ログに `❌ TUNNEL_TOKEN が一致しません` | Render の `TUNNEL_TOKEN` と違う値。合わせて再起動 |
| ログに `ハブ接続エラー: connect ECONNREFUSED` が続く | Render がスリープ中 or URL 間違い。**スリープ中なら `/__status` を一度開いてから 1分待って**再確認 |
| `/__status` が「上流に到達できません」 | 日本のマシンから `koetomo.fun:443` への送信が塞がれている(社内FW等)。`curl -I https://koetomo.fun` をそのマシンで実行して確認 |
| `/__status` が ❌ 403 のまま・出口IPが日本でない | リレーが動いているマシンが実は日本でない / VPN経由。`curl https://ipinfo.io` でそのマシンのIPの国を確認 |
| 出口IPは日本なのに 403 | そのプロバイダのIPレンジがブロック対象。別の回線(例: スマホのテザリング)で試す |
| 最初は動くがすぐ切れる | 日本のマシンのスリープ/省電力設定。`systemctl mask sleep.target suspend.target` 等で無効化 |

# 方式B: forward リレー(日本のクラウドサーバを使う)

日本の VPS / クラウドを借りられる場合はこちら。外向きのポート開放(TCP 8443)ができるサーバに
`relay/relay.js` を置き、Render の `RELAY_URL` に指定します。

- 実行: **[setup-oracle.sh](setup-oracle.sh)**(Oracle Cloud Always Free 東京/大阪 向け・$0)
  ```bash
  git clone https://github.com/shunichi19990314/koetomo-proxy.git
  cd koetomo-proxy/relay && bash setup-oracle.sh
  ```
  スクリプトが最後に `RELAY_URL=...` と `RELAY_CA_B64=...` の2行を出力するので、
  そのまま Render の Environment に貼り付けて Save するだけで切り替わります。

## Oracle Cloud Always Free の手順(要クレジットカード=本人確認のみ・$0)

1. https://signup.cloud.oracle.com でアカウント作成(メール・電話番号・カード本人確認あり)
2. **Compute → Instances → Create instance**

   | 項目 | 値 |
   |---|---|
   | Placement | Home Region が **Japan East (Tokyo)** / **Japan Central (Osaka)** |
   | Image | Ubuntu 22.04 / 24.04 (aarch64 または x86) |
   | Shape | **VM.Standard.A1.Flex**(ARM・Always Free、OCPU 1〜4 / RAM 6〜24GB)<br>在庫が無ければ **VM.Standard.E2.1.Micro**(AMD・Always Free) |
   | VCN | 「Create new VCN」でOK。**SSH(22)は自分のIPのみ**に絞る |

3. **VCN → Security List → Ingress Rules → Add Ingress Rules** で **TCP 8443**(Source `0.0.0.0/0`)を開放
   ※ これを忘れると Render からリレーに到達できず 502 になります
4. SSH して上記の `bash setup-oracle.sh` を実行

> ARM (A1.Flex) は東京リージョンで空きが無く「Out of capacity」になることがあります。
> その場合は AMD の E2.1.Micro を選ぶか、時間帯を変えて再試行してください。

## 方式B のセキュリティ

- Basic 認証(`RELAY_TOKEN`)必須。トークン無しは 407 で拒否
- 接続先は許可リスト(`koetomo.fun` / IP情報API のみ)。それ以外は 403
- CONNECT 先ポートは 443 / 80 のみ = オープンプロキシ化しません
- TLS は自己署名証明書を生成して `RELAY_CA_B64` でピン留め(盗聴・改ざん防止)

# 方法C: ブラウザだけ・クレカ不要(VPN拡張機能)

「アプリを入れたくない / クレカは使いたくない / 今すぐ試したい」場合の現実解です。
**ブラウザの拡張機能だけ**で日本IPを取得し、`https://koetomo.fun` を直接開きます
(Render のプロキシは使いません)。

## まず知っておくべきこと(2026年10月時点の実査結果)

「無料・クレカ不要・日本サーバ」の3条件を満たすサービスは、実はほとんど残っていません。
調べた結果は次のとおりです。

| サービス | 日本サーバ | クレカ | ブラウザだけ | 結論 |
|---|---|---|---|---|
| **Planet VPN lite**(拡張) | ✅ 無料・無制限 | 不要 | ✅ | **候補①** |
| **VeePN**(拡張) | ✅ 無料で日本IP | 不要 | ✅ | **候補②** |
| Proton VPN 無料 | △ 無料プールに日本はあるが**サーバ変更はランダム抽選+クールダウン(45秒→10分)** | 不要 | ❌(アプリ) | 日本を狙えないので不向き |
| Windscribe 無料 | ❌ 無料10カ国に日本なし(米/加/英/港/仏/独/蘭/瑞/諾/羅) | 不要 | ✅ | 不可 |
| TunnelBear 無料 | ❌ 2025年12月の改定で**国選択が有料化** | 不要 | ✅ | 不可 |
| Urban VPN | ✅ 無料 | 不要 | ✅ | **非推奨**(下記) |
| CroxyProxy 等のWebプロキシ | ❌ 有料でも独/英/西/米/加/以のみ | — | ✅ | 不可(403のまま) |
| 日本の無料クラウド/VPS | ✅ | **必須** | — | 不可 |
| VPN Gate(筑波大) | ✅ 日本サーバ多数 | 不要 | ❌(OSのVPN設定) | 手段はあるが下記注意 |

> ⚠️ **Urban VPN について**: 無料で日本IPが使えるため人気ですが、P2P方式(あなたの端末が他人の出口になる)で、
> さらに**拡張機能がユーザーの閲覧データをデータブローカーに送信していた**ことがセキュリティ各社から報告されています。
> 声ともはアカウントログインを伴うため、ここでは推奨しません。

## 手順(候補① Planet VPN lite)

1. Chrome / Edge で拡張機能ページを開く
   → `VPN Japan - Planet VPN lite Proxy`(Chrome ウェブストア)
2. **「Chromeに追加」** → 拡張アイコンをクリック → **Connect**
   (登録・メール・クレカ不要。国は日本固定)
3. 確認: ブラウザで `https://www.cmnwr.com/ipcheck` などを開き、**IPが日本(JP)**になっていればOK
4. **https://koetomo.fun** を開く → 本家がそのまま動きます

候補②は `VeePN` 拡張(Chrome ウェブストア)→ 接続先を **Japan** に設定、で同じです。

## ⚠️ 最大の注意: 音声通話が動かない可能性があります

声ともはボイスコミュニティで、ブラウザの音声通話は **WebRTC(UDP)** を使うのが普通です。
ところが **ブラウザ拡張型のVPNは HTTP/HTTPS/WebSocket しか通さず、WebRTC の音声メディアは通りません。**
結果として:

- ログイン・タイムライン・チャット → 動く可能性が高い
- **音声通話 → 繋がらない / 途中で切れる**
- さらに悪い場合、**WebRTC 経由であなたの本当のIPが漏れます**(=声とも側に日本国外IPが見える)

漏れの確認: 拡張を接続した状態で `https://browserleaks.com/webrtc` を開き、
`Public IP Address` が日本のVPNのIPになっているか(あなたのプロバイダのIPが出ていたら漏れています)。

**音声が駄目だった場合の本命**(すべてクレカ不要):

| 方法 | 内容 | 代价 |
|---|---|---|
| 方法A: リバーストンネル | 日本の常時ONマシンで `relay/reverse-tunnel.js` を起動(このリポジトリ) | マシンが1台必要・一度立てれば全端末で使える |
| VPN Gate(筑波大) | 日本サーバ多数・無料。**Windows/macOS/iOS の標準VPN機能(L2TP/SSTP)で接続できるのでアプリ追加も不要** | ボランティア運営のため品質が不安定。**運営者に通信が見える**ので、ログインを伴う用途ではアカウント情報漏えいのリスクがあります |
| 有料VPNの日本サーバ | 月¥500〜。WebRTCも含めて全部通るので最も確実 | クレカ必要(条件に合わない) |

## 使い方の安全ルール(無料VPN全般)

- **別のブラウザプロファイル**を作って、そこでだけ声ともを使う(拡張はあなたの全通信を復号して見られます)
- そのブラウザで **ネットバンキング・買い物・他のSNSのログインをしない**
- 声とものアカウントは **捨てメアド**で作る(無料VPN事業者は身元が確認できないため)
- 無料VPNは突然の方針変更・サーバ削除がよくあります(Proton/TunnelBear/Windscribe のように無料枠が縮小された例が多数)

# 方法D: 日本の無料公開プロキシ(何もインストールしない)

**拡張機能もアプリも使えない場合の最後の手段**です。
「日本にある公開プロキシ」を OS/ブラウザのプロキシ設定に入れるだけで、日本IPになります。
**2026年10月1日にこの環境から実測**し、`koetomo.fun` が **403 ではなく HTTP 200** を返したものを載せます。

## 実測で使えたプロキシ(2026-10-01)

> ⚠️ **公開プロキシは数時間〜数日で死にます。**下表は実測時点のスナップショットです。
> 繋がらなくなったら次の行を試すか、下の「[死んだら探し直す](#死んだら探し直す)」を実行してください。

| 優先 | プロキシ | 出口IP | 所在地 / 回線 | 実測結果(2回目 / 1回目) |
|---|---|---|---|---|
| **①** | **`38.175.202.151:443`** | 38.175.202.151 | 東京 / NetLab Global (AS979) | **200 ×3/3**(0.5〜1.7秒)/ 200 ×3/3 |
| **②** | **`45.43.60.220:8080`** | 45.43.60.220 | 東京 / UCloud (AS135377) | **200 ×3/3**(1.1〜1.8秒)/ 200 ×3/3 |
| ③ | `140.238.32.108:3128` | 140.238.32.108 | 東京 / Oracle Cloud (AS31898) | 200 ×1/3(残りタイムアウト)/ 200 ×3/3(0.3秒) |
| ④ | `111.119.162.248:10944` | (取得不可) | 日本 | 200 ×2/3(3.8〜6.5秒)/ 200 ×3/3 |

4件とも **CONNECT + TLS ハンドシェイクが成功し、証明書の検証も正常**(`CN=koetomo.fun` / `authorized=true`)でした。
= プロキシは暗号を復号できず、通信は koetomo.fun とエンドツーエンドで暗号化されたままです。
応答本文は 1420B(声ともの HTML シェル)で、`server: nginx` を確認しています。

## 設定方法(拡張機能もアプリも不要)

まず **`38.175.202.151` / ポート `443`** を入れてみてください(駄目なら ② 以下)。

**Firefox(一番簡単・ブラウザ内だけで完結)**
1. 右上メニュー → **設定** → 一般 → 一番下の **ネットワーク設定** → **設定…**
2. **手動でプロキシを設定する** を選択
3. **HTTPプロキシ**: `38.175.202.151` / **ポート**: `443`
4. ✅ **「HTTPS でもこのプロキシを使用する」に必ずチェック**
5. OK → `https://koetomo.fun` を開く

**Windows(Chrome / Edge はこの設定を使います)**
1. `Win + I` → **ネットワークとインターネット** → **プロキシ**
2. **手動プロキシセットアップ** を **オン**
3. アドレス `38.175.202.151` / ポート `443` → 保存
4. ブラウザを再起動して `https://koetomo.fun`

**macOS**
システム設定 → ネットワーク → Wi-Fi(使用中の回線)→ **詳細…** → **プロキシ** →
「Webプロキシ (HTTP)」と「Secure Webプロキシ (HTTPS)」の**両方**に `38.175.202.151` / `443` を入力 → 適用

**Android**
設定 → ネットワークとインターネット → Wi-Fi → 使用中の回線を長押し → **ネットワークを変更** →
詳細オプション → **プロキシ: 手動** → ホスト名 `38.175.202.151` / ポート `443` → 保存

**iPhone / iPad**
設定 → Wi-Fi → 使用中の回線の ⓘ → **HTTPプロキシ** → 手動 → サーバ `38.175.202.151` / ポート `443`

**確認**: `https://www.cmnwr.com/ipcheck` などを開いて IP が `38.175.202.151`(日本)になっていれば成功です。

## ⚠️ 使う前に必ず読むこと

- **公開プロキシは誰が運営しているか分かりません。** HTTPS は暗号化されたままなので中身は読まれませんが、
  **どのサイトに行ったかは全部見えます**。ネットバンキング・買い物・他のSNSには絶対に使わないでください
- **証明書エラー(警告)が出たら絶対に「続行」を押さないでください。** 中間者攻撃のサインです
  (今回実測した4件は証明書検証が正常=復号していないことを確認済みですが、保証はできません)
- 声とものアカウントは**捨てメアド**で作ることを強くおすすめします
- **数時間〜数日で死にます。** 繋がらなくなったら次の候補を試すか、下の「探し直す」を実行してください
- **音声通話(WebRTC/UDP)は HTTP プロキシを通りません。** タイムライン・チャット・WebSocket 系の機能は動きますが、
  音声だけが繋がらない場合はこれが原因です(→ 方法A のリバーストンネルなら音声も通ります)
- 帯域は他の利用者と共有なので、混雑すると遅くなります

## 死んだら探し直す

リポジトリにスキャナを入れてあります(Node がある環境で):

```bash
npm install
npm run scan:jp      # 無料プロキシ一覧から「日本かつ koetomo.fun が 403 以外」を自動で探す
npm run verify:jp    # 見つかったプロキシの速度・安定性・TLS を詳しく検証
```

## Render 側で使う(全端末から設定ゼロで使える)

上のプロキシを **Render の環境変数に入れるだけ**で、ブラウザ側は何も設定せずに
`https://koetomo.onrender.com` を開くだけで済むようになります。

```
RELAY_LIST     = 38.175.202.151:443,45.43.60.220:8080,140.238.32.108:3128,111.119.162.248:10944
RELAY_DEEP_PROBE = 1
```

`RELAY_DEEP_PROBE=1` にすると、候補の実測時に **アプリ本体(約5MBの `main.*.js`)を実際にダウンロード**して
速度まで判定します。「HTML は 200 なのにページが真っ白」になる遅いプロキシを自動的に外せます。

> **API が別ドメインな件は対応済みです。** 声ともは Web本体(`koetomo.fun`)とは別に
> `a.koetomo.fun` / `api.meetscom.com` / `mtrcs.koetomo.fun` を叩きます(同じ ALB なので同様に 403)。
> プロキシがこれらを `/__up/<host>/...` に書き換えて自分経由にするため、**追加設定は不要**です
> (既定の `UPSTREAM_HOSTS` に入っています)。
> 実測では `/__up/a.koetomo.fun/users/1` が **404 `{"error":"not_found"}`(=API 本体の応答)** を返し、
> 地域ブロックを突破できていることを確認しました。
> なお **音声通話(WebRTC)は SkyWay(NTT)の SFU にブラウザが直接接続**し、その認証サーバ
> `skyway-auth.meetscom.com` は地域ブロックされていない(CORS も `*`)ため、プロキシ不要で通る見込みです。

`RELAY_LIST` に複数の候補を入れると、プロキシ本体が:

- 起動時と **5分ごと**に全候補を実測し、**「200が返る → 速い」順に自動で並べ替え**
- リクエスト中に接続エラーや ELB の 403 を検出したら **即座に次の候補へ回転して自動リトライ**
- 死んだ候補は無効化し、復帰したら自動で再利用
- 状態は **`/__relay`**(JSON)、**`/__relay?recheck=1`**(即実測)、**`/__relay?rotate=1`**(強制切替)で確認
- `/__status` にも候補ごとの実測結果(ステータス・応答時間・出口IP・国)を一覧表示

つまり「1つ死んでも勝手に次へ切り替わる」ので、`RELAY_LIST` に多めに入れておくほど安定します。
19項目の自動テスト(`test/pool-smoke.js`)で、**壊れた候補を先頭に置いても 200 が返ること**・
**全滅時にハングせず失敗すること**・**復帰を自動検出すること**を検証済みです。

> 注意: Render の無料プランはスリープします。また Render のサービスが `suspended` になっている場合は
> ダッシュボードで **Resume Service** が必要です。

# それでも開けないときの最終確認

`/__status` は「事実」を全部出します。ここを見れば原因は一意に決まります。

| `/__status` の表示 | 意味 | 対処 |
|---|---|---|
| ✅ 上流に受け入れられています | 完成。`/` を開けば声ともが動きます | — |
| ❌ HTTP 403 / 経路=直接接続 | 日本の出口がまだ無い | 上の方式A か 方式B を実施 |
| ❌ HTTP 403 / 出口IPが日本 | そのIPレンジがブロックされている | 別の回線・別のマシンに切り替え |
| ⚠️ 上流に到達できません | リレーが落ちている/設定ミス | 上の「切り分け」表へ |
| `/__hub` の relays が空 | 日本のマシンが未接続 | リレーの起動とトークンを確認 |
| `/__relay` の候補が全部 ❌ | 公開プロキシが全滅 | `npm run scan:jp` で探し直す / `RELAY_LIST` を差し替え |
